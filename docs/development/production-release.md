## Rollback and interruption recovery

On start/health/frontend failure the script stops the candidate, restores the previous shared pointer and starts/verifies the previous backend. The SAME persistent ledger remains; new attempts/cooldowns/auth errors must survive rollback. A rollback is another stop/start, never a parallel instance. If stopping or recovery fails, the script exits nonzero; inspect transaction JSON and service status privately. Do not claim restoration from a pending record.

For a later authorized rollback, pass the previous compatible release directory to the SAME explicit activation command. It applies the same checks; automatic fallback on a failed rollback returns to the pre-command release. There is no `--force`, quota reset, ledger restore or release deletion.

For power loss/SIGKILL, automatic rollback cannot run. With authorization, acquire the same `/opt/coinmind/activation.lock` using `flock` before manual intervention; stop the service, verify no process/port owner, inspect `current` and latest transaction. If `current.next` exists, investigate it and move it to a uniquely named evidence path (do not blindly delete). Restore a reviewed compatible previous pointer via a new temporary symlink and atomic rename, then start the service and check backend/frontend. Never replace a running process's ledger or restore an older ledger snapshot. If state is unreadable or compatibility is uncertain, leave Gemini disabled and escalate; never reset state to make health pass. No automatic cleanup is provided.
